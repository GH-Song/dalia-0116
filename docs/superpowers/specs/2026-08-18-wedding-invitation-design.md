## 1. 목적

송국호 · 최은호의 결혼식을 위한 **모바일 우선 단일 페이지 청첩장**을 만들어 GitHub Pages에 배포한다.
한 번 쓰고 버리되 그 한 번을 실패하면 안 되는 물건이다. 목적함수는 **견고함과 로딩 속도**이며,
재사용성·추상화는 값어치가 없다.

## 4. 아키텍처 결정

### AD-1. Vanilla HTML/CSS/JS. 프레임워크·npm·번들러 없음

3개월 뒤 `npm install`이 도는지 확인해야 하는 상태를 만들지 않는다.
빌드는 Python 스크립트 몇 개(폰트 서브셋·검증·용량 게이트)와 문자열 치환뿐이다.

### AD-2. 팔레트는 `theme.css` 한 파일로 격리

`style.css`에 하드코딩된 색상값은 **0개**. 모든 색은 `var(--…)`.
테마 교체 = `theme.css` 교체. 이 규칙은 CI에서 강제한다(§10).

### AD-3. 장식은 PNG가 아니라 인라인 SVG 라인아트

**무료 자산 조사 결과 (2026-08-18).** 직접 그리기 전에 오픈 라이선스 자산을 먼저 찾아봤고
전부 부적합했다. 같은 조사를 반복하지 않도록 기록해 둔다.

| 출처 | 결과 |
|---|---|
| Wikimedia Commons | PD 식물도감 다수. 표본 대지·학명 캡션·해부도가 포함된 **학술 도판**이라 잘라내야 하고, 짙은 석판화라 온실 톤과 불일치 |
| Openverse (CC0/PDM) | "watercolor flower" 계열 **0건** |
| GitHub | 웨딩 보태니컬 벡터 세트 없음 |
| Openclipart (CC0) | 결과는 있으나 **아마추어 클립아트**. 넣으면 품질이 내려감 |
| publicdomainvectors · svgrepo · rawpixel | 403 / 429 / 403 (봇 차단) |

결론: 무료·오픈 라이선스로 웨딩 수준의 수채 일러스트는 구할 수 없다. 직접 그리되
**평면적으로 보이지 않게 하는 네 가지**를 지킨다 — (1) 농담(濃淡) 레이어, (2) 크기·각도 흔들림으로
개체 변이, (3) 앞뒤 3층, (4) 밑동에서 부챗살로 벌어지는 구도.
줄기를 세로로 나란히 세우면 식물도감 표본 배열처럼 보인다.

**수채 질감이 필요하면 유료 스톡을 사는 수밖에 없다.** 벡터의 상한은 '정제된 미니멀 보태니컬'이다.
(v2에서 사용자가 "오픈된 일러스트 파일 최대 활용"을 다시 요청했으나, 위 조사 결과가 근거라
재탐색 대신 벡터 품질을 올리는 쪽을 택한다.)

**v2 — 라인아트에서 '벡터 수채'로.** 윤곽선 중심 라인아트는 절제된 온실 컨셉에는 맞았지만
화사한 웜톤에서는 앙상해 보인다. 새 장식은 **반투명 꽃잎을 3~4겹 겹쳐 쌓는다** — 겹침이 수채의
번짐처럼 톤을 만들므로 그라데이션 `<defs>` 없이도 부드럽고, id 충돌 걱정 없이 인라인 반복이 가능하다.
소재는 겨울에 피는 따뜻한 꽃 **동백(camellia)** 을 중심으로 목화·유칼립투스 잎·안개꽃 점·눈꽃.

**다색(多色) 규칙** — 단색 실루엣을 벗어나되 테마 격리는 유지한다. SVG 안에서 색을 직접 찍지 않고
`<g class="flora-bloom">`(꽃) / `<g class="flora-leaf">`(잎) / `<g class="flora-stem">`(줄기·점) 처럼
**부위별 wrapper 클래스**를 두고, `style.css`가 각 클래스에 `color: var(--color-*)`를 배정한다.
내부는 전부 `fill/stroke="currentColor"` — 테마 교체가 여전히 파일 하나로 끝난다.

배치: 히어로 상단 garland(중앙 동백 + 좌우로 흘러내리는 잎), 섹션 코너 스프레이(교대로 좌/우),
디바이더 배너(좌우 대칭 스프레이), 푸터 스프레이.
결과: (a) 팔레트 교체 시 장식 색이 자동으로 따라옴, (b) 장식 하나가 2MB → 2~5KB, (c) 레티나에서 안 깨짐.

**개화 서사 (v2.2 — "봄을 기다림"의 장식 버전).** 페이지를 내려갈수록 개화가 진행된다:

- 히어로·전반 코너(모시는 글·예식일) — 만개 + 봉오리 혼합. **기존 자산 그대로** (이미 봉오리 포함)
- 후반 코너(마음 전하실 곳·공유) — `corner_full`: 봉오리 자리에 만개 한 송이 추가 + 안개꽃·낙화 꽃잎 증량
- 푸터 — `bloom_sprig`: 만개 동백이 중심에 오는 가지. 곁에 봉오리를 남겨 "기다림 → 도착"이 한 그림에

**품질 제1원칙 (사용자 요구):** 서사를 위해 장식의 밀도·화려함을 깎지 않는다. 봉오리든 만개든
모든 자산은 그 자체로 화려하고 예뻐야 하며, 컨셉 때문에 못생겨지는 안은 기각.
신규 자산은 **독립 시드**로 생성한다 — 기존 4종의 난수 스트림을 건드리면 승인된 그림이
전부 재추첨되므로, 새 함수는 시작 시 자체 시드로 리셋하고 ASSETS 목록 끝에만 추가한다.
(주의: 현재 HTML의 corner·divider·sprig 인라인은 과거 스트림 산출물이라 생성기 전량 재실행과
일치하지 않는다. 기존 자산을 다시 뽑아 붙이지 말 것.)

  실시간 임베드 지도는 하객이 실제로 조작하지 않으며, 딥링크가 더 나은 결과를 준다.
  딥링크는 좌표·장소ID 대신 **검색 스킴**(`nmap://search?query=`)을 쓴다 (2026-08-18 결정).
  장소ID를 박으면 API 키 없이 얻기 어렵고 홀이 등록을 바꾸면 깨진다. 앱이 없으면 스킴이
  조용히 실패하므로 1.4초 뒤에도 화면이 그대로면 웹 지도로 넘긴다.
- **공유**: `og:` 메타태그(카톡에 링크를 붙이면 미리보기 카드가 자동 생성됨) + 링크 복사 버튼.
  카카오 JS SDK는 "페이지 안의 공유 버튼"만 추가할 뿐이며, 실제 전파는 신랑신부가 직접 뿌리는 링크가 대부분이다.

### AD-5. RSVP 백엔드는 Google Apps Script → Google Sheets

집계 화면을 만들지 않아도 되는 것이 결정적 이유. 제출이 시트에 쌓이고 `SUM` 한 줄로 정산이 끝난다.

## 6. RSVP 데이터 모델

### 폼

```
구분        ○ 신랑측  ○ 신부측              (필수)
성함        ____________                     (필수)
참석 여부   ○ 참석합니다  ○ 어렵습니다      (필수)

  ↓ '참석' 선택 시에만 펼침
식사하실 분        − 2 +
답례품 받으실 분   − 1 +
  → "총 3분 참석" 자동 표시

전하고 싶은 말  ____________               (선택, 한 줄)
```

**총 참석 인원을 따로 묻지 않고 두 숫자의 합으로 계산한다.** 이유:
(a) 하객이 헷갈릴 여지가 없고, (b) 합이 안 맞는 입력이 구조적으로 불가능하며,
(c) 웨딩홀에 넘길 숫자(식사 n명 / 답례품 n개)가 가공 없이 그대로 나온다.

**연락처는 받지 않는다.** 하객 전화번호를 모으는 순간 우리가 관리 책임을 지는 개인정보가 된다.

### 시트 스키마

| 열 | 타입 |
|---|---|
| timestamp | ISO8601 |
| side | `groom` \| `bride` |
| name | string |
| attending | `yes` \| `no` |
| meal_count | int (불참 시 0) |
| gift_count | int (불참 시 0) |
| message | string (선택) |

### 실패 처리

제출 실패 시 "카카오톡으로 알려주세요" 폴백 문구를 띄운다. 막다른 길을 만들지 않는다.
Apps Script는 `Content-Type: text/plain`으로 POST해 CORS preflight를 회피한다.

### 모션

"조용히 피어나는" — 빠르고 화려한 모션 금지. 전환은 ease-out 600~900ms.

- 배경: **옅은 눈 입자**가 아주 느리게 (밀도 낮게, opacity 0.40~0.85). 꽃잎 입자는 블러시.
- **입자 페이드 (v2.3 — v2.2 계절 전이를 대체)**: 눈·꽃잎 혼합은 히어로~모시는 글까지만.
  모시는 글 하단을 지나며 재생성 쿼터가 줄고, 쿼터를 넘는 입자는 **2~3초에 걸쳐
  옅어지다 잠든다** — 낙하가 느려(초당 7~23px) 화면 밖까지 기다리면 1분씩 잔상이
  남기 때문. 그 아래로는 **꽃잎 3~4장만 은은하게**(눈꽃 확률 0으로 수렴, 알파 최대
  40% 감쇠). 위로 되돌아오면 쿼터가 회복되어 다시 눈이 내린다. 기준선은 `.greeting`
  하단, 페이드 구간 약 1.2 뷰포트.
  눈꽃은 **이중 스트로크 음영**(웜 세피아 `--snow-flake-shade` 밑선 + **순백 불투명** 결정 윗선)으로
  굽는다 — 밝은 아이보리 배경에서는 세피아 음영이, 어두운 사진·스크림 위에서는 흰 코어가
  대비를 만들어 어느 배경에서든 결정이 읽힌다. v2.1: 음영은 옅게(알파 0.38), 그만큼 코어를
  순백(#FFF 불투명)으로 — 어둡게 누르는 대신 하얗게 띄우는 쪽. 글자 가독을 해치지 않는
  선에서만 (밀도는 그대로 낮게)
- 히어로 (v2): 로드 시 garland → 스크립트 → 이름 → 날짜 순 **순차 fade-up** (스태거 120ms)
- 스크롤: IntersectionObserver 진입 시 fade-in + translateY(20px → 0).
  섹션 안의 주요 블록은 `transition-delay` 스태거(80~120ms)로 한 박자씩 늦게 (v2)
- 마이크로: 계좌 복사 시 체크 마크 + 햅틱(가능 시)
- `prefers-reduced-motion: reduce` → 눈 입자 OFF, fade-in 즉시 표시

## 8. 타이포그래피 · 폰트 서브셋

### 폰트 계통을 둘로 분리 — 두부(□) 방지의 핵심

```css
--font-display: "NanumMyeongjo-subset", "Apple SD Gothic Neo", "Malgun Gothic", serif;
--font-ui:      -apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo",
                "Malgun Gothic", "Noto Sans KR", sans-serif;
```

- `--font-display` = **고정 텍스트 전용** (인사말, 이름, 날짜, 섹션 제목)
- `--font-ui` = **사용자 문자열이 지나갈 수 있는 모든 곳**

영문 세리프(Cormorant Garamond)를 서브셋해 self-host한다. 전부 OFL이라 서브셋 재배포 가능.

| NanumMyeongjo 400 | 본문 고정 텍스트 | 전체 수집 문자 |
| **NanumMyeongjo 700** (v2) | 섹션 제목·이름·홀명 | `data-face="bold"` 요소에서 추출 |
| Cormorant Garamond 400 | 아이브로우·날짜·달력·D-day | 라틴·숫자 |
| **Allura 400** (v2) | 히어로 문구·`&`·Thank you | `data-face="script"` 요소에서 추출 + `&` |

~~스크립트체(Allura)는 쓰지 않는다~~ → **v2에서 번복.** '절제' 논거는 온실 컨셉의 것이었고,
새 방향은 장식 밀도를 올리는 쪽이다. 단, 스크립트는 **고정 영문 3곳**(히어로 문구 · & · Thank you)에만.
한글·사용자 문자열에는 절대 쓰지 않는다.

**`data-face` 규칙 (v2)** — 스타일 훅과 서브셋 추출 마커를 한 속성으로 통일한다.
`[data-face="bold"]`/`[data-face="script"]` 는 style.css 의 폰트 지정 셀렉터인 **동시에**
`tools/subset-fonts.py` 의 문자 수집 대상이다. 마커 없이 볼드/스크립트를 쓰면 글리프 게이트가
잡아낸다. 스타일과 서브셋이 구조적으로 어긋날 수 없다.

숫자는 `lnum`(라이닝)을 강제한다 — Cormorant 기본값인 올드스타일 숫자는 `01`이 `OI`로
읽혀서 어르신 하객에게 불리하다.

### 두부 방지 4층

1. **스코프 분리** — 사용자 문자열이 들어가는 DOM에 `data-user-content` 속성을 달고
   `[data-user-content] { font-family: var(--font-ui) !important }`.
   **특히 "○○○님, 참석으로 접수되었습니다" 같은 제출 확인 메시지가 최대 위험 지점이다.**
   입력창만 막고 여기를 놓치기 쉽다. 토스트·에러 문구도 포함.
2. **서브셋을 빌드 산출물로** — `tools/subset-fonts.py`가 `index.html`에서 실제 쓰인 문자를 추출해
   `pyftsubset`에 먹인다. 카피를 고치면 서브셋이 자동으로 따라온다. 수동 동기화를 없앤다.
3. **CI 게이트** — `tools/check-glyphs.py`가 고정 텍스트의 모든 코드포인트를 서브셋 폰트와 대조.
   하나라도 빠지면 **빌드 실패**.
4. **폴백 스택** — 위 셋이 다 뚫려도 마지막 방어선. iOS/Android/Windows/macOS 모두 한글 시스템 폰트를
   갖고 있어 두부는 구조적으로 발생 불가. 최악이 "글자 하나가 다른 폰트로 보임"이다.

추가로 서브셋 생성 시 **한국인 성명 빈출 음절을 여유분으로 얹는다.** 몇 KB로 안전 마진을 산다.

## 10. 용량 예산 — CI에서 강제

**코드는 gzip 전송 크기로 잰다** (2026-08-18 구현 중 결정). GitHub Pages가 텍스트 자산을
항상 압축해 보내므로 하객의 로딩 속도를 정하는 값이 그쪽이다. 비압축 크기로 재면
주석을 지우는 것이 성능 개선으로 잘못 계산된다. woff2·PNG는 이미 압축돼 있어 원본 크기로 잰다.

| 항목 | 예산 | 측정 |
|---|---|---|
| HTML + CSS + JS | 38 KB | gzip |
| 폰트 (서브셋 4종, v2) | 82 KB | 원본 |
| SVG 장식 · 약도 | (HTML에 인라인이라 위에 포함) | — |
| 히어로 이미지 | 120 KB | 원본 |
| **첫 화면 소계** | **~270 KB** | |
| 갤러리 5장 (lazy, AVIF) | 각 ~100 KB | 원본 |
| **전체** | **~800 KB** | |

v2 조정: 폰트 60→85 KB (명조 700 부분 서브셋 + Allura 추가), 코드 30→35 KB (섹션 장식
SVG 인라인 증가). **첫 화면 270 KB · 전체 800 KB 상한은 그대로다** — 협상 불가인 것은 이
두 상한이고, 내부 배분은 실측으로 관리한다.

2026-08-18 재배분: 코드 35→38 KB, 폰트 85→82 KB. 교통 안내 강화(§2 실측 반영)로 코드가
34.7 KB까지 차오른 상태에서 텍스트가 늘었고, 폰트 실측이 57.9 KB로 여유가 크므로 그쪽에서
가져왔다. 첫 화면 소계는 불변.

`revfactory`가 약 20MB인 것 대비 **25배 축소**가 목표.
`tools/check-budget.sh`가 초과 시 배포를 실패시킨다. 숫자로 관리하지 않으면 반드시 샌다.

**CI 게이트 4종 (모두 배포 차단)**
1. 용량 예산 초과 — `tools/check-budget.sh`
2. 폰트 글리프 커버리지 미달 — `tools/check-glyphs.py`
3. `style.css`에 하드코딩된 색상 리터럴 존재 — `tools/check-colors.sh`
4. **저장소에 실제 계좌번호 존재** — `tools/check-privacy.sh` (2026-08-18 추가).
   규칙 1은 사람의 주의력에 맡기기엔 대가가 크다. 자리표시자 4개가 그대로인지,
   계좌 섹션에 더미가 아닌 숫자가 없는지 기계가 확인한다.

## 11. 개인정보 취급

### 원칙

**계좌번호·전화번호는 git에 절대 들어가지 않는다.**

- `index.html`에는 `__ACCT_GROOM__` 같은 자리표시자만 둔다

### 노출 축소

- `robots.txt` + `<meta name="robots" content="noindex,nofollow">` — 검색 색인 제외
- **URL은 `/wedding`이 아니라 추측하기 어려운 슬러그** (레포 이름 = URL 슬러그)
- 계좌는 클릭해서 펼치기 (기본 접힘)

**알려진 한계 (수용함):** GitHub Pages 프로젝트 사이트는 무료 계정에서 레포가 public이어야 하고,
public 레포는 `github.com/GH-Song?tab=repositories`에 노출된다. 슬러그는 URL 추측과 검색 색인을 막을 뿐
프로필 열람은 막지 못한다. 레포에 개인정보가 없으므로 실질 위험은 낮다고 판단해 수용한다.
